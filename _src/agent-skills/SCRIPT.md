# Skills 分享逐字稿

> 总时长：50 分钟（30 分钟主体 + 10 分钟实操 + 10 分钟答疑）
> 听众：技术团队 + 管理层
> 目标：科普 + 布道

---

## 第一部分：痛点共鸣（5 分钟）

### 【开场 - 场景带入】

大家好，今天想跟大家聊一个话题。

在开始之前，我想先问大家一个问题：

**你们有没有遇到过这种情况？**

你让 Claude 或者 Cursor 帮你写代码，结果它写出来的东西，完全不符合你们团队的规范。

比如：
- 数据库字段命名，你们用的是 `created_at`，它给你写 `createdAt`
- SQL 查询，你们明确禁止 `SELECT *`，它上来就是 `SELECT *`
- 代码风格，你们有自己的一套，它完全不知道

然后你告诉它："我们有规范，请按规范来。"

它说："好的，明白了。"

然后下一个任务，它又忘了。

**你又得重复一遍。**

这种感觉，像不像在带一个实习生——聪明是聪明，但你得反复教，而且他每天早上来都失忆？

---

### 【放大痛点】

这个问题往深了想，其实挺严重的：

**对个人来说**——效率损耗。你本来想让 AI 帮你省时间，结果你花了大量时间在"教育"它。

**对团队来说**——知识没法沉淀。张三教了 Claude 一遍规范，李四来了又得教一遍。每个人都在重复劳动。

**对管理者来说**——你没法扩展。AI 的能力上限，被"它不懂我们的规矩"这件事卡住了。

所以问题的本质是什么？

---

### 【定义问题】

我用一句话总结：

> **Agent 有智能和能力，但不一定有我们实际工作需要的专业知识。**

它像什么？

**它像一个 IQ 300 的数学天才。**

你让它报税，它可以从第一性原理推导出税法，但过程很慢、不稳定、容易出错。

而你真正需要的，是一个 **20 年经验的税务专家**——他用成熟的流程、深厚的领域知识，给你可靠、高效、一致的输出。

**关键任务，我们需要专家，不需要天才。**

那问题来了：怎么把一个"天才"变成"专家"？

---

## 第二部分：核心洞察（5 分钟）

### 【旧范式的问题】

过去业界的思路是什么？

**一个领域，造一个专门的 Agent。**

财务有财务 Agent，代码有代码 Agent，研究有研究 Agent。

每个 Agent 都有自己的 prompt、自己的工具、自己的配置。

这个思路的问题是：

1. **不可扩展**——你有多少领域，就要造多少 Agent
2. **很脆弱**——一个 Agent 坏了，整个流程就断了
3. **最关键的：知识无法共享**——你在财务 Agent 里沉淀的经验，代码 Agent 用不上

每次都在重复造轮子。

---

### 【新洞察】

后来我们发现一个事情：

**代码，是通往数字世界的通用接口。**

什么意思？

与其给每个领域造专门的工具，不如让一个通用的 Agent，通过最基础的能力——读文件、写文件、跑命令——去完成几乎所有数字化任务。

API 调用？它可以。
数据分析？它可以。
文件操作？它可以。
数据库查询？它可以。

**核心脚手架可以薄到只有 Bash 和文件系统。**

这就是为什么 Claude Code、Cursor 这些工具这么强大——它们不是给每个场景写死逻辑，而是让 AI 用代码去解决问题。

但是！

通用能力有了，**专业知识怎么办？**

你们团队的规范、你们公司的 SOP、你们行业的最佳实践——这些东西，AI 不知道。

---

### 【制造"啊哈"时刻】

假如有这样一个东西：

- 你把你的经验、规范、流程**写下来**
- AI 需要的时候，**自动加载**
- 你写一次，**整个团队都能用**
- 而且它还能**不断积累、持续进化**

是不是就解决了刚才所有问题？

**这个东西，就叫 Skills。**

---

## 第三部分：方案介绍（10 分钟）

### 【Skills 是什么】

Skills 是什么？

**说白了，就是文件夹。**

我知道这听起来有点反高潮，但这种简单是刻意的。

一个 Skill 是一个组织好的文件集合，为 Agent 打包可组合的程序性知识。

里面可以有什么？

1. **指令文件**（SKILL.md）——告诉 AI 该怎么做
2. **可执行脚本**——AI 可以直接调用的工具
3. **模板、代码库、资源文件**——任何辅助材料

---

### 【最简单的例子】

让我给大家看一个最简单的 Skill：

```
my-skill/
└── SKILL.md
```

就这么一个文件夹，里面一个 Markdown 文件。

SKILL.md 长什么样？

```markdown
---
name: sql-standards
description: 团队 SQL 编写规范，写查询时使用
---

# SQL 编写规范

## 命名规则
- 表名：小写 + 下划线，如 user_orders
- 字段名：小写 + 下划线，如 created_at

## 查询规范
- 禁止 SELECT *
- 必须指定字段列表
```

**会写 Markdown，就会写 Skill。**

这不是工程师专属的能力。产品经理能写、运营能写、财务法务都能写。

---

### 【怎么工作的】

接下来大家肯定想问：这玩意怎么工作？

原理很简单，两个机制：

**机制一：渐进式披露**

打个比方——你去图书馆。

你不会一进门就读完所有书，对吧？你先看书架上的书名和简介，找到你需要的，再打开细读。

Skills 也是这样。

- 一开始，Claude 只看到每个 Skill 的**名字和描述**（元数据）
- 这样它能"感知"到几百个 Skills 的存在
- 只有当它判断"这个任务需要用这个 Skill"，才会加载完整内容

这解决了一个很现实的问题：**上下文窗口是有限的**，你不可能把所有知识一股脑塞给它。

**机制二：脚本作为可修改的工具**

和写死的 API 不同，Skill 里的脚本是可读的、可改的。

如果 AI 发现脚本有 bug，或者不适配当前场景，它可以**自己改**。

这解决了"代码卡住"的问题——AI 不会被死板的工具限制住。

---

### 【怎么用】

怎么开始用？三步：

1. **创建文件夹**，写好 SKILL.md
2. **放到指定目录**（比如 `.claude/skills/`）
3. **没有第三步了**

Claude 会自动发现、自动判断、自动使用。

**你不用告诉它"请使用 xxx skill"。**

它自己会判断：这个任务跟哪个 Skill 相关，需不需要加载。

这个设计很重要——**零摩擦**。你不用改变任何工作习惯，只是多了一个文件夹而已。

## 第四部分：价值展望（5 分钟）

### 【组织级知识库】

现在我们把视角拉高一点，想想这件事对组织意味着什么。

**一个人创建的 Skill，能立即升级组织内所有 Agent 的能力。**

想象一下这个场景：

老王是你们团队的数据库专家，他把 20 年的 SQL 经验写成了一个 Skill。

从这一刻起，团队里每个人的 Claude，都具备了老王的 SQL 能力。

新人入职，不用培训，Claude 已经懂你们团队的规矩了。

**这是知识的复利效应。**

传统的知识管理是什么？写文档、做培训、靠老带新。效率很低，而且人走了知识就流失了。

有了 Skills：

- 知识被**显式捕获**——不在人脑子里，在文件里
- 知识被**自动共享**——不用培训，AI 自动用
- 知识在**持续进化**——发现问题就更新 Skill

---

### 【生态趋势】

这不是我们自己在玩，这是整个行业的趋势。

**Anthropic 已经把 Skills 开放为开放标准**，网站是 agentskills.io。

**主流平台都在跟进**——VS Code、GitHub Copilot、Cursor、甚至 OpenAI 也悄悄采用了结构相同的架构。

已经有很多合作伙伴在贡献官方 Skills——Atlassian、Figma、Notion、Stripe...

而且最有意思的是：**非技术人员也在写 Skill**。

财务在写报销审批流程，法务在写合同审核规范，招聘在写面试评估标准。

这已经不是玩具了，**这是方向**。

---

### 【这是 AI 的应用层】

如果你熟悉计算机历史，会发现这个模式我们见过：

- **模型 = 处理器**——需要巨额投资，蕴含巨大潜力，但单独存在用处有限
- **Agent Runtime = 操作系统**——编排资源，提供核心能力，让处理器变得有用
- **Skills = 应用**——这是真正解决具体问题的层

PC 时代，应用层爆发了。移动时代，App Store 爆发了。

AI 时代，**Skills 就是应用层**。

数百万开发者将在这里编码领域专业知识，为世界解决具体问题。

## 第五部分：行动指引（5 分钟）

### 【不同角色怎么开始】

讲了这么多，怎么开始？我给不同角色一些建议：

**如果你是开发者：**

今天就写一个最简单的 Skill。

从哪开始？**从你最常重复说的那句话开始。**

你跟 Claude 说过多少遍"我们用的是 TypeScript 不是 JavaScript"？把它写下来，就是一个 Skill。

**如果你是非技术人员：**

把你的工作流程写成文档。

比如你是财务，你审批报销单的流程是什么？判断标准是什么？例外情况怎么处理？

写下来，找开发同事帮你包成 Skill。

**如果你是管理者：**

挑一个小团队，pilot 两周。

不用大张旗鼓，找 3-5 个愿意尝试的人，让他们先跑起来。观察效果，收集反馈，再决定要不要推广。

---

### 【怎么衡量效果】

管理者肯定会问：怎么衡量效果？

理想的指标当然是：效率提升了多少？采纳率多少？返工率降低了多少？

但说实话，**这些很难自动化统计**。

我们现在能做的：

1. **统计 Skill 数量**——团队沉淀了多少知识
2. **统计使用次数**——哪些 Skill 被高频使用
3. **收集主观反馈**——定期问大家感觉怎么样
4. **观察留存**——有没有人用了一段时间又删掉

不完美，但**先跑起来**。

Anthropic 官方 Roadmap 里有 Testing & Evaluation，未来工具会更成熟。

## 第六部分：实操演示（10 分钟）

### 【演示目标】

接下来我们现场演示：**从零创建一个 Skill，让 Claude 自动使用它。**

我会用一个大家都能理解的例子：**SQL 编写规范**。

### 【步骤一：创建文件夹】

首先，在项目根目录创建 Skills 目录：

```bash
mkdir -p .claude/skills
```

然后创建我们的 Skill 文件夹：

```bash
mkdir .claude/skills/sql-standards
```

### 【步骤二：写 SKILL.md】

创建核心文件：

```bash
touch .claude/skills/sql-standards/SKILL.md
```

内容如下：

```markdown
---
name: sql-standards
description: 团队 SQL 编写规范。当编写 SQL 查询、创建表、修改数据库 schema 时使用此规范。
---

# SQL 编写规范

## 命名规则

### 表名
- 使用小写字母
- 单词之间用下划线分隔
- 使用复数形式
- 示例：`user_orders`, `product_categories`

### 字段名
- 使用小写字母
- 单词之间用下划线分隔
- 时间字段统一用 `_at` 后缀：`created_at`, `updated_at`
- 布尔字段用 `is_` 或 `has_` 前缀：`is_active`, `has_permission`

## 查询规范

### SELECT 语句
- **禁止使用 SELECT ***
- 必须明确列出需要的字段
- 字段较多时每个字段单独一行

```sql
-- 正确
SELECT
    id,
    username,
    email,
    created_at
FROM users
WHERE is_active = true;

-- 错误
SELECT * FROM users;
```

### JOIN 规范
- 必须使用显式 JOIN 语法
- 禁止在 WHERE 中做隐式连接
- JOIN 条件用 ON，过滤条件用 WHERE

## 索引规范
- 主键字段必须有索引
- 外键字段必须有索引
- WHERE 和 ORDER BY 高频使用的字段考虑加索引
```

### 【步骤三：测试效果】

现在我们来测试。打开 Claude Code，直接让它写一个查询：

```
帮我写一个 SQL 查询，获取所有活跃用户的订单信息
```

**观察点**：
- Claude 会自动发现并加载 sql-standards Skill
- 生成的 SQL 会遵循我们定义的规范
- 不会出现 `SELECT *`
- 命名会符合我们的约定

### 【演示要点】

1. **自动发现**：我们没有告诉 Claude "请使用 sql-standards"，它自己判断的
2. **按需加载**：只有写 SQL 时才会加载，写其他代码不会干扰
3. **立即生效**：不需要重启、不需要配置，放进去就能用

### 【进阶演示（如果时间允许）】

展示 Skill 可以包含脚本：

```bash
# 创建一个检查脚本
touch .claude/skills/sql-standards/check-sql.sh
```

```bash
#!/bin/bash
# 检查 SQL 文件是否包含 SELECT *

if grep -r "SELECT \*" "$1"; then
    echo "❌ 发现 SELECT *，请修改为明确的字段列表"
    exit 1
else
    echo "✅ SQL 规范检查通过"
    exit 0
fi
```

Claude 可以在生成 SQL 后自动调用这个脚本来验证。

## 第七部分：Q&A 预案（10 分钟）

### 常见问题准备

**Q: Skills 和 MCP（Model Context Protocol）什么关系？**

A: 它们是互补的。MCP 是让 AI 连接外部工具和数据源的协议，解决的是"能力扩展"问题。Skills 解决的是"知识注入"问题——怎么把专业知识教给 AI。你可以在 Skill 里调用 MCP 工具，它们配合使用。

**Q: 会不会泄露公司数据？**

A: Skills 是完全本地的，就是你项目里的文件夹。它不会上传到任何地方。你的 Skill 内容只会在本地被 Claude 读取，和你的代码一样安全。

**Q: 和 CLAUDE.md / .cursorrules 什么区别？**

A: CLAUDE.md 是项目级的全局指令，每次对话都会加载。Skills 是按需加载的——只有 AI 判断任务相关时才会加载。这样更高效，也更模块化。你可以有几十个 Skills，但 CLAUDE.md 只有一个。

**Q: 多个 Skills 冲突了怎么办？**

A: 目前需要人工协调，确保 Skills 之间不冲突。实践中建议：1）Skill 职责单一，不要太大；2）命名和描述写清楚，减少歧义；3）团队定期 review Skills 库。

**Q: 我怎么知道 Claude 用了哪个 Skill？**

A: 在 Claude Code 里，当 Skill 被加载时会有提示。你也可以让 Claude 在回答时说明它参考了哪些 Skills。

**Q: 非技术人员怎么用？**

A: 他们可以写 Skill 的内容（就是 Markdown 文档），让技术同事帮忙放到正确的位置。或者用 Claude 自带的 "Skill Creator" 功能，直接对话让 Claude 帮你创建 Skill。
