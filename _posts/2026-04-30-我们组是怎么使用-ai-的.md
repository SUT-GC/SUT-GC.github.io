# 我们组是怎么使用 AI 的：从 MCP、Skill 到研发工作流

这篇文章算是一篇组内分享文档的底稿。

我想聊的不是“AI 最近又出了什么新模型”，也不是单纯介绍某个工具怎么用。更想回答一个实际一点的问题：**AI 发展到今天，对一个研发团队来说，到底可以怎么用？**

我会先简单回顾一下 AI 的发展阶段，然后重点讲两个最近很关键的概念：MCP 和 Skill。最后再结合我们组的使用方式，聊聊 AI 在写代码和排障里的落地方式。

先说结论：

**AI 的价值，不是让某个人偶尔变快，而是让一个团队把好的工作方法持续复用起来。**

---

## 一、AI 发展到今天，已经不只是“问答工具”

过去我们提到 AI，很多时候想到的是一些比较“后台”的能力。

比如图片识别、语音识别、推荐系统、搜索排序、风控模型。这些能力很早就存在，也确实改变了很多产品体验。但对大多数普通用户来说，AI 当时并不是一个可以直接协作的对象。它更多是藏在系统后面，帮助系统做判断、做分类、做推荐。

真正让大家明显感受到变化的，是大模型出现之后。

以 ChatGPT 为代表的大模型，把 AI 从一个“系统能力”变成了一个可以直接对话的助手。我们可以直接用自然语言描述问题，让它写文档、总结材料、生成代码、解释报错、翻译内容，甚至帮我们一起讨论方案。

这个阶段的变化很关键。

过去使用软件，我们需要学习软件的操作方式。现在很多时候变成了：我们只要把目标说清楚，AI 就可以帮我们完成一部分工作。

但很快大家也会发现，只会聊天的 AI 其实还有明显边界。

它可以告诉你“应该怎么做”，但不一定能真的帮你做。它可以根据已有上下文回答问题，但不知道你公司内部系统里的真实数据。它可以写代码片段，但如果不了解完整项目结构，就很容易写出看起来对、实际跑不通的代码。它也可以分析报错，但如果拿不到日志、监控、发布记录、配置文件，它的判断就只能停留在猜测层面。

所以 AI 的下一步，很自然地走向了 Agent。

所谓 Agent，可以简单理解为：AI 不只是回答问题，而是可以围绕一个目标，自己拆解步骤、调用工具、观察结果，再继续调整。

比如在写代码场景里，一个 Agent 可以做的不只是“帮我写一个函数”。它可以先读需求，再查项目结构，找到相关文件，提出修改方案，改代码，跑测试，看到报错后继续修，最后生成提交说明。

这时候 AI 的角色就变了。

它不再只是一个“问答窗口”，而开始变成一个可以参与实际工作流的协作者。

但 Agent 真正要好用，有两个问题必须解决。

第一个问题是：**AI 怎么连接外部世界？**

我们的代码在 Git 仓库里，文档在知识库里，问题在工单系统里，日志在日志平台里，数据在数据库里。如果 AI 不能访问这些上下文，它就很难真正完成任务。

第二个问题是：**AI 怎么稳定复用我们的经验？**

同样是“帮我排查问题”，不同团队的排查路径可能完全不一样。有人先看日志，有人先看监控，有人先查发布记录，有人先看链路追踪。同样是“写代码”，每个团队也会有自己的分支规范、代码风格、测试要求和 Review 标准。

如果这些经验每次都靠人重新写在 Prompt 里，那 AI 的使用就很难稳定，也很难规模化。

于是就出现了两个很重要的方向：**MCP** 和 **Skill**。

MCP 主要解决的是“连接”的问题。  
Skill 主要解决的是“经验复用”的问题。

MCP 让 AI 可以通过统一协议连接外部工具和数据。Skill 则让 AI 可以按某个稳定的方法去完成一类任务。

这两个东西放在一起看，其实代表了 AI 从“会回答”走向“能干活”的关键一步。

## 二、MCP 和 Skill 是什么

### MCP：让 AI 接上外部工具和数据

MCP，全称是 Model Context Protocol，可以理解为一个让 AI 连接外部系统的开放协议。

Anthropic 在 2024 年 11 月发布 MCP 时，提到的核心问题是：随着 AI 助手越来越强，它们仍然受限于数据孤岛。也就是说，模型本身能力再强，如果拿不到业务系统里的数据，或者不能调用真实工具，它的作用还是有限的。

过去要让 AI 接入一个工具，通常需要为这个工具单独做一套集成。

接 GitHub，要写一套。  
接数据库，要写一套。  
接 Slack、Google Drive、Postgres、日志平台，又要分别写一套。

这种方式的问题是很明显的：集成成本高，维护成本高，而且每个工具的接入方式都不一样。

MCP 的思路是提供一个统一标准。

外部系统可以通过 MCP Server 暴露能力。AI 应用或者 Agent 可以作为 MCP Client 去连接这些 Server。这样一来，AI 不需要为每个系统重新理解一套接入方式，而是可以通过统一协议拿到上下文、调用工具、执行动作。

举个简单例子。

如果我们有一个日志系统，希望 AI 能帮忙查日志。过去可能需要专门写一段插件逻辑，让 AI 知道怎么访问这个日志系统。但如果日志系统提供了 MCP Server，AI 就可以通过 MCP 标准接口去查询日志、读取结果，再结合问题继续分析。

所以 MCP 的价值，可以概括成一句话：

**它让 AI 从一个封闭的对话框，变成了可以连接真实系统的工作入口。**

不过 MCP 解决的是“能不能接上”的问题。它并不直接解决“接上之后怎么把事情做好”的问题。

这就需要 Skill。

### Skill：把团队经验打包给 AI

Skill 可以理解为一种“任务能力包”。

它通常不是一句 Prompt，而是一个包含说明、步骤、脚本、模板、示例和注意事项的文件夹。AI 在遇到某类任务时，可以加载对应 Skill，然后按照里面沉淀的方法去做事。

比如我们有一个“代码 Review Skill”，里面可以写清楚：

- Review 前先看需求背景
- 先检查核心逻辑，再看边界条件
- 必须关注是否有测试
- 对安全、性能、兼容性做专项检查
- 最后输出 Review 结论和修改建议
- 如果涉及数据库变更，要额外检查迁移脚本
- 如果涉及接口变更，要检查调用方影响

这就比简单说一句“帮我 Review 一下代码”稳定得多。

再比如一个“线上排障 Skill”，里面可以沉淀：

- 先确认故障现象和影响范围
- 再拉时间线
- 检查最近发布和配置变更
- 分析日志中的异常关键词
- 对比正常请求和异常请求
- 建立可能原因列表
- 每个原因都要有验证方法
- 最后输出根因、修复动作和复盘建议

这样 AI 不只是“帮忙想想”，而是会沿着团队认可的排障路径往下走。

这也是 Skill 对团队特别有价值的地方。

团队里真正稀缺的，往往不是某一个人的一次性 Prompt，而是那些已经被验证过、可以反复使用的方法。

### Skill 和 Prompt 有什么区别？

很多人第一次听到 Skill，会觉得它是不是就是“高级一点的 Prompt”。

我觉得不是。

Prompt 更像是一次性的指令。  
Skill 更像是可复用的工作手册。

Prompt 通常写在一次对话里，适合临时任务。Skill 可以长期保存，适合反复出现的任务。

Prompt 依赖当下这个人是否把话说清楚。Skill 可以把团队共识提前沉淀进去。

Prompt 往往只有文字。Skill 可以包含脚本、模板、示例、参考文件，甚至可以规定工具调用方式。

比如“帮我写一篇技术分享”是 Prompt。

但如果我们有一个“技术分享 Skill”，它可以规定：

- 开头不要写成宣传稿
- 必须先讲真实背景
- 中间要有具体案例
- 不要堆概念
- 结尾要回到团队实践
- 输出格式要适合飞书文档或者博客

这就不是一句 Prompt 能稳定解决的。

### Skill 和 MCP 有什么区别？

如果用一个简单比喻：

**MCP 是接口，Skill 是方法。**

MCP 解决的是 AI 怎么连接工具。Skill 解决的是 AI 怎么完成任务。

MCP 让 AI 能“拿到东西”。Skill 告诉 AI “拿到东西以后怎么处理”。

比如排障场景：

MCP 可以让 AI 连接日志平台、监控系统、工单系统、Git 仓库。Skill 则告诉 AI：先看什么，后看什么，如何判断优先级，怎么避免误判，最后怎么输出结论。

再比如写代码场景：

MCP 可以让 AI 访问代码仓库、Issue、CI、文档。Skill 则告诉 AI：怎么理解需求，怎么拆任务，怎么写测试，怎么提交 PR，怎么让代码符合团队规范。

所以 MCP 和 Skill 不是替代关系，而是互补关系。

MCP 让 AI 有能力接触更多上下文。Skill 让 AI 用正确的方法处理这些上下文。

### 为什么我觉得 Skill 对团队更重要？

对一个团队来说，真正要把 AI 用起来，不只是“接几个工具”这么简单。

工具接入当然重要，但如果没有稳定的方法，AI 接入越多工具，反而可能越混乱。它可能查了很多信息，但不知道哪些重要；也可能做了很多动作，但不符合团队习惯。

Skill 的价值在于，它可以把团队已有的经验结构化。

以前这些经验可能分散在不同人脑子里：

- 老同事知道线上问题应该先看哪个监控面板
- 资深开发知道某个模块不能随便改
- TL 知道 Review 时最容易漏掉哪些边界
- 测试同学知道哪些场景一定要覆盖
- 运维同学知道某类告警通常和什么配置有关

这些经验如果不沉淀，每次都要靠人提醒。但如果沉淀成 Skill，AI 就可以在执行任务时主动加载。

这会带来几个变化。

第一，AI 的输出会更稳定。不是每次都靠临场发挥，而是按照固定流程做事。

第二，团队经验可以复用。不是只有某个人会用 AI，而是整个团队都能基于同一套方法使用 AI。

第三，新人上手更快。新人不一定马上理解所有系统细节，但可以先通过 Skill 了解团队处理问题的标准路径。

第四，复杂任务更容易被拆解。因为 Skill 可以把复杂任务拆成标准步骤，让 AI 一步一步执行，而不是一上来就给一个大而全的答案。

所以我觉得，MCP 更像是 AI 基础设施的一部分。而 Skill 更像是团队 AI 使用能力的沉淀方式。

如果一个团队只是偶尔用 AI 问问题，那 Prompt 就够了。如果一个团队希望 AI 真正进入研发、排障、Review、文档、运营等工作流，那 Skill 会变得越来越重要。

## 三、我们组怎么应用 AI

我们组目前对 AI 的使用，主要可以分成两个方向：**写代码** 和 **排障**。

这两个方向有一个共同点：我们不是单纯让 AI “给建议”，而是尽量让 AI 进入实际工作流，帮助我们减少重复劳动、提升信息处理效率。

### 写代码方向

写代码方向，我们可以分成两类：一类是本地插件，一类是远端工作空间。

#### 本地插件：适合小范围、高频、即时的代码辅助

本地插件更适合日常开发中的即时辅助。

比如我们正在看一个模块，想快速理解某段逻辑；或者有一个小需求，需要改几个文件；又或者遇到一个报错，想让 AI 帮忙解释一下调用链。

这类场景的特点是：上下文相对集中，反馈链路短，开发同学自己也能快速判断 AI 结果是否靠谱。

一个典型流程是：

1. 开发同学先把需求描述给 AI
2. AI 根据当前打开的文件或项目上下文理解代码
3. AI 给出实现思路
4. 开发同学确认方向
5. AI 辅助修改代码
6. 本地运行测试或启动服务验证
7. 开发同学做最后调整并提交

这里 AI 的价值主要体现在几个方面：

- 帮我们更快理解陌生代码
- 帮我们补齐样板代码
- 帮我们发现遗漏的边界条件
- 帮我们解释报错
- 帮我们生成测试用例
- 帮我们节省在重复性代码上的时间

但本地插件也有边界。

它更适合“人主导，AI 辅助”的场景。如果任务很大，涉及多个模块、完整测试、环境依赖和 PR 流程，本地插件就不一定是最合适的方式。

这时就可以考虑远端工作空间。

#### 远端工作空间：适合更完整的任务交付

远端工作空间更像是让 AI 在一个独立环境里完成任务。

它可以拉代码、建分支、查文件、改代码、运行测试，甚至生成 PR。相比本地插件，它更适合中等复杂度以上的需求。

一个比较理想的流程是：

1. 我们先把需求写清楚
2. AI 读取需求，分析相关代码
3. AI 输出实现计划
4. 人先 Review 计划，确认方向
5. AI 开始修改代码
6. AI 运行单测、构建或必要的验证命令
7. 如果失败，AI 根据报错继续修复
8. 最后生成变更总结和 PR
9. 人进行 Code Review

这里有一个关键点：我们不能把 AI 当成一个完全自动提交代码的黑盒。

更合理的方式是，把 AI 当成一个执行力很强的初级协作者。

它可以帮我们完成大量检索、修改、验证和总结工作，但方向判断、架构取舍、风险评估，仍然需要人来把关。

尤其是在 Review 阶段，人不能省。

AI 可以生成代码，但代码是否真的符合业务预期，是否影响历史逻辑，是否有隐含风险，最终还是要由开发同学负责。

#### Code Review：AI 可以辅助，但不能替代责任

在 Code Review 阶段，AI 的作用也很明显。

它可以帮我们检查：

- 这次变更是否覆盖了需求
- 有没有明显的边界条件遗漏
- 是否缺少测试
- 是否有潜在空指针、异常处理、并发问题
- 是否引入性能问题
- 是否影响旧逻辑
- 命名和结构是否清晰
- PR 描述是否完整

但我觉得 AI Review 的定位应该是“辅助检查”，而不是“最终审批”。

因为 AI 容易发现一些模式化问题，但对业务背景、历史包袱、团队取舍，不一定理解得足够深。

所以更好的方式是：让 AI 先扫一遍，帮我们找低级问题和遗漏点。人再做最终 Review，把重点放在业务正确性和架构合理性上。

这样可以减少 Review 中的重复劳动，也能提高 Review 质量。

### 排障方向

第二个方向是排障。

排障其实是非常适合 AI 参与的场景。因为排障过程中有大量信息需要快速处理：

- 日志
- 监控
- 报错堆栈
- 用户反馈
- 发布时间线
- 配置变更
- 代码变更
- 上下游依赖
- 历史类似问题

过去这些信息都要靠人一点点看。AI 的优势是可以快速读大量文本，提取异常点，帮我们建立假设。

但这里也要注意，排障不能直接让 AI “猜原因”。

更好的方式是让 AI 帮我们做结构化分析。

一个比较合理的流程是：

1. 先描述故障现象  
   什么时间发生、影响哪些用户、具体表现是什么、是否可复现、是否有明显错误码。

2. 收集上下文  
   相关日志、监控截图或指标、最近发布记录、配置变更、相关代码片段、依赖服务状态。

3. 让 AI 提炼异常点  
   哪些日志是关键异常，哪些指标变化最明显，时间线是否和某次发布重合，报错是否集中在某个接口、租户、机房或版本。

4. 让 AI 建立可能原因列表  
   每个原因要说明依据，不能只给结论。每个猜测都要配一个验证方法。

5. 人执行验证  
   查具体数据、回滚配置、对比版本、复现问题，验证假设是否成立。

6. 最后让 AI 辅助生成复盘  
   故障时间线、根因、修复过程、影响范围、后续改进项。

在这个过程中，AI 最有价值的地方不是“神奇地一下子找到根因”，而是帮助我们更快把混乱信息整理成清晰路径。

它能减少排障时的信息噪音。也能提醒我们不要漏掉一些常见检查项。尤其是在日志很多、链路比较长的时候，AI 可以帮我们节省大量阅读和归纳时间。

不过排障场景也必须保留人的判断。

因为线上问题往往有业务上下文。有些现象看起来像代码 Bug，实际可能是配置问题。有些看起来像下游异常，实际可能是调用方参数变化。AI 可以帮我们提出假设，但最终还是要靠数据验证。

所以我们在排障中使用 AI 的原则应该是：

**让 AI 帮我们加速分析，但不要让 AI 直接替我们下结论。**

## 四、AI 真正改变的是团队工作方式

回头看这轮 AI 的变化，我觉得它最重要的地方，不是多了一个聊天工具，也不是某个模型又变强了多少。

真正的变化是：AI 开始进入我们的工作流。

它可以参与写代码，参与 Review，参与排障，参与文档整理，参与知识沉淀。它不再只是一个“有问题时问一下”的工具，而是可以在很多任务中承担一部分执行工作。

但这也带来一个新的问题：如果每个人都只是按照自己的习惯随手用 AI，团队很难真正获得稳定收益。

有人用得很好，有人用得一般。有人能写出高质量 Prompt，有人不知道怎么描述问题。有人会让 AI 先读上下文再动手，有人一上来就让 AI 直接改代码。这样最后的效果会非常不稳定。

所以我觉得，团队使用 AI 的关键，不是追逐每一个新工具，而是要逐渐沉淀自己的 AI 工作方式。

这里面有三个层次。

第一层，是工具使用。  
比如我们会用本地插件、远端工作空间、AI Review、日志分析工具。

第二层，是流程嵌入。  
比如需求开发怎么用 AI，Code Review 怎么用 AI，线上排障怎么用 AI，复盘总结怎么用 AI。

第三层，是经验沉淀。  
也就是把我们已经验证过的方法，沉淀成 Skill、模板、检查清单和标准流程。

只有到第三层，AI 才不只是个人效率工具，而会变成团队能力的一部分。

对我们组来说，后面真正值得做的事情，可能不是简单地讨论“哪个 AI 工具更好用”，而是要持续回答几个问题：

- 哪些工作适合交给 AI 做第一版？
- 哪些环节必须由人来判断？
- 哪些经验应该沉淀成 Skill？
- 哪些场景需要接入 MCP 或内部工具？
- AI 生成的结果应该如何验证？
- 怎么让不同成员都能稳定地用好 AI？

我觉得这才是 AI 在团队里的长期价值。

它不是替代我们思考，也不是替代我们负责。它更像是把很多重复、琐碎、信息密集型的工作压缩掉，让人可以把更多精力放在判断、设计、沟通和决策上。

最后可以用一句话总结：

**MCP 让 AI 连接系统，Skill 让 AI 继承经验，而真正决定效果的，是团队能不能把这些能力放进自己的日常工作流里。**
