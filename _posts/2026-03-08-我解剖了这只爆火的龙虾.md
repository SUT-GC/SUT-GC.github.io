最近 OpenClaw（前身 Clawdbot）火遍硅谷到北京，有人说它是"AI 助手的终局形态"。一个开源项目，两个月内斩获 **14 万+ GitHub Stars**，让一堆人去买 Mac Mini 专门跑它。

作为程序员，我第一反应不是去用它，而是去看代码。

于是我把整个仓库 clone 下来，读了一遍。7783 个文件，29MB TypeScript 源码，502 个 agent 相关模块。这篇文章就是我的读后感——**从技术视角，搞清楚它到底是怎么做到的**。

结论是：没那么玄。后面我也顺手整理了一条**用现有开源工具自己搭一个的路径**，想抄作业的直接拉到最后。

---

## 它究竟是什么？

用一句话描述：**OpenClaw 是一个跑在你本地机器上的、以消息 App 为操控界面的持久化 AI Agent**。

它不是聊天机器人，不是 Zapier，也不是套壳 AI。核心差异在三个词：

- **本地运行**：数据不上云，你的代码、文件、记忆全在本机
- **持久化**：24 小时在线，有 cron 定时任务，会主动联系你
- **消息 App 为界面**：你用 WhatsApp / 微信 / Telegram 跟它聊，它在后台对着你的电脑干活

---

## 整体架构：五层结构

读完代码，我把它的架构抽象成五层：

```
┌─────────────────────────────────────┐
│         消息渠道层 (Channels)         │  ← WhatsApp / Telegram / Discord / iMessage...
├─────────────────────────────────────┤
│          Gateway 核心层              │  ← 消息路由、认证、会话管理
├─────────────────────────────────────┤
│          Agent 执行层                │  ← 调用 LLM、执行工具、生成回复
├─────────────────────────────────────┤
│          记忆系统层 (Memory)          │  ← SQLite + 向量嵌入 + FTS 全文检索
├─────────────────────────────────────┤
│          技能/插件层 (Skills)         │  ← 1Password / GitHub / Notion / 天气...
└─────────────────────────────────────┘
```

下面逐层拆解。

---

## 第一层：消息渠道——用 Baileys 协议搞定 WhatsApp

很多人好奇：WhatsApp 并没有开放 API，OpenClaw 是怎么接入的？

答案在 `extensions/whatsapp/` 目录。它用的是 **Baileys**，一个逆向工程了 WhatsApp Web 协议的开源库。

原理非常优雅——本质上就是模拟你电脑浏览器开着 WhatsApp Web：

```
手机 WhatsApp ←→ WhatsApp 服务器 ←→ 本地 Gateway（Baileys 长连接）
```

**关键点**：连接是从你本地主动发起的（出站），不需要公网 IP。WhatsApp 服务器会通过 WebSocket 长连接把消息实时推过来。就像你打开 WhatsApp Web 一样，只不过接收端是 OpenClaw 的 Gateway，而不是浏览器。

渠道层的代码在 `extensions/` 目录下，每个渠道独立一个包：

```
extensions/
├── whatsapp/      ← Baileys 协议
├── telegram/      ← Telegram Bot API
├── discord/       ← Discord.js
├── slack/         ← Slack Web API
├── imessage/      ← AppleScript（仅 macOS）
├── signal/        ← signal-cli
├── feishu/        ← 飞书 Webhook
└── ...（还有十几个）
```

每个渠道实现一套统一的 `ChannelPlugin` 接口，包含：认证、收发消息、媒体处理、群组管理等能力。这个设计让主核心完全不关心下层是什么 App，消息统一流入 Gateway。

## 第二层：Gateway——整个系统的心脏

`src/gateway/` 是整个项目最核心的目录。Gateway 是一个常驻后台的 HTTP 服务（默认端口 18789），负责：

**1. 消息路由**

收到消息后，Gateway 会根据发送人、群组、配置等判断：这条消息该不该响应？该交给哪个 Agent？

```typescript
// src/channels/run-state-machine.ts 节选
// 用状态机管理每个对话的运行状态
export function createRunStateMachine(params: RunStateMachineParams) {
  let activeRuns = 0;
  // ...
  // 心跳机制，60秒汇报一次状态
  const DEFAULT_RUN_ACTIVITY_HEARTBEAT_MS = 60_000;
```

**2. 会话管理**

每个对话有独立的 session，存储在本地文件系统。每次 LLM 调用都会带上完整的历史上下文——OpenClaw 用文件系统实现了跨进程的"记忆"。

**3. Boot 机制**

这是一个很有意思的设计。Gateway 启动时会检查工作目录下的 `BOOT.md`：

```typescript
// src/gateway/boot.ts
function buildBootPrompt(content: string) {
  return [
    "You are running a boot check. Follow BOOT.md instructions exactly.",
    "BOOT.md:",
    content,
    // ...
  ].join("\n");
}
```

如果 `BOOT.md` 里写了"每次启动后发消息给我说'已上线'"，它就会这么干。这个机制让你可以用自然语言配置 Agent 的启动行为。

**4. 认证管理**

支持多种 API Key 和 OAuth 认证方式，覆盖主流国内外模型（GLM、DeepSeek、通义千问等），统一抽象。

## 第三层：Agent 执行——本地 Coding Agent

这层是最有趣的部分。OpenClaw 的 Agent 执行实际上是在调用一个本地 Coding Agent 的 agent 模式。

`src/agents/` 目录下有 502 个文件，负责：

- 组装 prompt（把用户消息、历史、记忆、工具列表拼成 LLM 的输入）
- 调用 LLM API，流式接收输出
- 解析工具调用，执行本地命令
- 把结果发回给用户

工具执行是通过沙箱隔离的：

```
src/agents/sandbox/      ← Docker 沙箱（可选）
extensions/diffs/        ← 文件 diff 工具
extensions/llm-task/     ← 子任务分发
```

`--dangerously-skip-permissions` 这个臭名昭著的 flag，就是绕过工具执行的权限确认——开了之后 Agent 可以无需你确认就跑命令。懂的人知道这是生产力利器，不懂的人开了等于让 AI 随便操作你的电脑。

**ACP（Agent Communication Protocol）**

`src/acp/` 目录实现了一个 Agent 间通信协议。这允许 OpenClaw 孵化子 Agent、并行执行多个任务、Agent 和 Agent 之间互相通信。这是它"多智能体"能力的底层基础。

## 第四层：记忆系统——向量数据库 + SQLite + FTS

这是 OpenClaw 最被低估的部分，也是它跟普通聊天机器人最本质的区别。

看 `src/memory/memory-schema.ts`，它的记忆系统建在本地 SQLite 上，有三张核心表：

```sql
-- 记忆文件索引
CREATE TABLE files (
  path TEXT PRIMARY KEY,
  hash TEXT NOT NULL,
  mtime INTEGER NOT NULL,
  ...
);

-- 分块嵌入（向量记忆）
CREATE TABLE chunks (
  id TEXT PRIMARY KEY,
  path TEXT NOT NULL,
  text TEXT NOT NULL,
  embedding TEXT NOT NULL,  -- 向量，JSON格式
  updated_at INTEGER NOT NULL,
  ...
);

-- 嵌入缓存（避免重复计算）
CREATE TABLE embedding_cache (
  provider TEXT NOT NULL,
  model TEXT NOT NULL,
  hash TEXT NOT NULL,
  embedding TEXT NOT NULL,
  ...
);
```

同时还有一张 FTS5 全文检索虚拟表，支持关键词模糊检索。

记忆系统支持多种嵌入后端：

```
src/memory/embeddings-openai.ts   ← OpenAI
src/memory/embeddings-gemini.ts   ← Google
src/memory/embeddings-mistral.ts  ← Mistral
src/memory/embeddings-ollama.ts   ← 本地 Ollama
src/memory/embeddings-voyage.ts   ← Voyage
```

检索时用的是 **MMR（Maximal Marginal Relevance）** 算法（`src/memory/mmr.ts`），同时考虑相关性和多样性，避免检索结果都是重复内容。

每次对话，Agent 会先检索记忆，把相关片段注入 prompt，这就是它"记得你之前说过什么"的原理。

## 第五层：Skills 技能系统——插件市场

`skills/` 目录和 `extensions/` 目录是两套不同的扩展机制：

- **Extensions**：核心功能扩展，消息渠道、认证提供商等，随主程序一起发布
- **Skills**：轻量级技能包，社区发布，用户按需安装

一个 Skill 本质上就是一个 YAML/Markdown 描述文件 + 若干工具定义：

```
skills/github/
├── skill.md      ← 自然语言描述这个 skill 干什么
└── tools.yaml    ← 工具定义（调用哪些命令/API）
```

社区的 ClawHub 上目前有超过 13,000 个社区技能。这是 OpenClaw 最大的护城河——生态。

## 如果你要自己实现一个，怎么做？

读完代码，我总结了一个最小可行架构（MVP）：

**最简版本（一周能做出来的）**

```
1. 选一个消息渠道
   - Telegram Bot API（最简单，官方支持，不用逆向）
   - 微信：用 wxauto / WeChatFerry（需要 Windows）

2. 写一个消息监听服务
   - 收到消息 → 调用 LLM → 把回复发回去
   - Node.js / Python 都行，100行代码搞定

3. 接入一个 LLM Agent
   - 传入对话历史，保持上下文连贯
   - 给 Agent 挂几个工具：读写文件、执行命令、搜索网页

4. 加持久化记忆
   - 最简单：把对话存 SQLite，每次检索最近 N 条
   - 进阶：加向量嵌入，做语义搜索
```

**进阶版本（需要一个月）**

```
5. 加 cron 定时任务（node-cron 库）
6. 加沙箱隔离（Docker 容器执行工具）
7. 加多渠道支持（抽象出 Channel 接口）
8. 做 Web 控制台（实时查看 Agent 状态）
```

OpenClaw 能做到今天这个规模，是因为它把**每一层都做得足够健壮**：记忆系统有批量嵌入、缓存、故障恢复；渠道层有重连、降级、健康检测；Agent 层有沙箱、权限控制、审计日志。

这些工程细节，才是真正的护城河。

**捷径：用 Cody 作为 Agent 内核**

如果你不想从零搭 Agent 执行层，有一个开源项目值得关注：[CodyCodeAgent/cody](https://github.com/CodyCodeAgent/cody)。

它是一个 Python 编写的 AI 编码 Agent 框架，28 个内置工具（文件读写、Shell 执行、子 Agent 编排、MCP 集成）已经帮你把最重的部分造好了。用它当内核，你只需要补上 OpenClaw 缺失的那几块：

```
你的消息渠道适配层（Telegram / 微信 / WhatsApp）
              ↓
     消息路由 + 记忆检索（补写）
              ↓
     Cody SDK（内核，开箱即用）
              ↓
     把结果推回渠道
```

对照 OpenClaw 的五层架构，Cody 覆盖了 **Agent 执行层** 的绝大部分，你只需要额外实现：

| 需要补的模块 | 工作量 | 说明 |
|---|---|---|
| 消息渠道适配 | 小 | Telegram 接入不超过 50 行 Python |
| 常驻 Gateway | 小 | 在 Cody Web API 外包一层消息监听 |
| 向量记忆系统 | 中 | Cody 有 session 但无长期向量记忆，需补 |
| BOOT.md 启动钩子 | 小 | 在初始化时注入 system prompt 即可 |
| Cron 定时任务 | 小 | `apscheduler` 库几行搞定 |

核心调用方式极简：

```python
from cody import AsyncCodyClient

async with AsyncCodyClient(workdir="/path/to/project") as client:
    # 把 Telegram 收到的消息直接传进来
    result = await client.run(user_message, session_id=chat_id)
    # 把结果推回 Telegram
    await bot.send_message(chat_id, result.output)
```

OpenClaw 的 TypeScript 体量太大，直接魔改门槛很高。Cody 是 Python、MIT 协议、结构清晰，更适合作为自建方案的起点。

## 一点思考

OpenClaw 的成功，技术本身只占一半原因。

另一半是：**它抓住了"AI 从工具变成员工"这个转折点**。

过去我们用 AI，是"我有问题，我去问 AI"。OpenClaw 的范式是"AI 在后台替你盯着，有情况它找你"。这个主被动关系的翻转，才是它让人感到震撼的原因。

代码并不神秘。但选择在这个时间点把这些东西整合在一起，做出来，让它能用——这是真本事。
