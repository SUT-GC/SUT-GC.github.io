![我造了一只自己的龙虾](https://int32-blog.oss-cn-beijing.aliyuncs.com/uploads/codyclaw-cover.jpg)

上一篇我解剖了 OpenClaw，拆出了八层架构，末尾说：下一篇动手造一只。

抱歉鸽了一周多。不过这段时间也没闲着——我们先给龙虾造了大脑，然后再给它装上身体。

这个大脑叫 **[Cody](https://github.com/CodyCodeAgent/cody)**，是我开源的 Python AI Agent Runtime 框架。简单说，它帮你把造 Agent 时最烦的事都包了：带了29 个内置工具（文件读写、Shell、代码搜索、网页访问）、多模型支持（Claude / GPT / Gemini / DeepSeek）、流式输出、会话管理、权限控制、human in loop等等——`pip install cody-ai` 就能用。其实单说 Cody 这个话题就够写出几篇文章了，后面专门刨析。

这篇的事情很简单：回到上一篇的八层架构，看看要造一只最小可用的龙虾，到底得实现哪些东西，哪些可以跳过，哪些可以偷懒。然后我们真的造了一只出来——叫 [CodyClaw](https://github.com/CodyCodeAgent/codyclaw)，跑在飞书上，效果还不错。

## 回到那八层：我们到底要实现什么

上一篇拆出的八层架构是这样的：

![八层架构，我们做哪些？](https://int32-blog.oss-cn-beijing.aliyuncs.com/uploads/codyclaw-8layers.jpg)

| 层 | OpenClaw 做了什么 | 我们要不要做 |
|---|---|---|
| ① 入口层 | CLI、TUI、Web UI、macOS App、iOS、Android | 不做。飞书就是我们的入口 |
| ② 消息渠道层 | WhatsApp（逆向协议）、Telegram、Discord、Slack 等 10+ | 只做飞书。官方 SDK，WebSocket 长连接 |
| ③ Gateway 层 | 消息路由、会话管理、状态机、健康监控、Boot 机制、执行审批 | **必须做**。这是心脏 |
| ④ Hooks & Cron 层 | 事件总线、cron 定时任务 | 做 cron。hooks 暂时不需要 |
| ⑤ Agent 执行层 | Claude Code CLI / Codex CLI，双引擎，嵌入式运行，ACP 多 Agent 协议 | **这是最重的一层——也是 Cody 帮我们省掉的** |
| ⑥ LLM Provider 层 | 28 个供应商、Auth Profile 轮换、模型自动发现、浏览器自动化 | 模型调用交给 Cody，浏览器不做 |
| ⑦ 记忆与技能层 | 向量数据库 + FTS 混合检索、ClawHub 插件市场 | 简化版记忆，技能用 SKILL.md |
| ⑧ 基础设施层 | 配置系统、执行安全、路径沙箱 | 基础的配置管理就够 |

一看就清楚了：八层里有三层是"锦上添花"（入口、多渠道、基础设施），两层可以大幅简化（记忆、Provider），一层可以部分做（Hooks & Cron 只做 Cron）。

真正绕不过去的就两件事：**Gateway**（消息怎么进来、怎么路由、怎么出去）和 **Agent 执行**（AI 怎么想、怎么调工具、怎么管上下文）。

## 如果全部自己写，有多累

![第⑤层自己写，有多累？](https://int32-blog.oss-cn-beijing.aliyuncs.com/uploads/codyclaw-complexity.jpg)

先说 Agent 执行层，也就是上面第 ⑤ 层。OpenClaw 这层的代码量最大，因为它要解决的问题最多：

- **工具系统**：文件读写、Shell 执行、代码搜索、网页访问……每个工具都要定义参数格式、处理返回值、做安全校验。OpenClaw 光工具相关的代码就有几十个文件。
- **流式输出**：LLM 一个 token 一个 token 地吐，你要接住、拼装、分发给前端。中间还可能穿插工具调用——AI 说到一半突然要读个文件，读完再接着说。
- **会话上下文**：每次调 LLM 都是无状态的，你得自己管理对话历史、做 token 计数、在上下文快爆的时候做压缩。
- **权限控制**：AI 想删文件，你得拦住它问用户。这涉及到中断执行流、等待用户回复、再恢复执行——异步状态机。
- **多模型适配**：Anthropic 和 OpenAI 的 API 格式不一样，工具调用的协议也不一样，你要写适配层。

如果这些全自己写，光这一层就够折腾几周。而且这些东西跟"龙虾"本身的业务逻辑没关系——不管你是造龙虾还是造别的什么 Agent 应用，这些脏活都得干一遍。

这就是我们造 Cody 的原因。

## Cody 帮我们省掉了什么

![造龙虾的两种方式](https://int32-blog.oss-cn-beijing.aliyuncs.com/uploads/codyclaw-compare.jpg)

Cody 是 Agent 的运行时引擎。Cody可以以SDK的方式，丝滑的嵌入到你的代码中，帮助大家用几行代码，就能让AI赋能自己的系统。上面说的那些脏活，它全包了：

```python
client = AsyncCodyClient(
    model="claude-sonnet-4-6",
    api_key=config.api_key,
    base_url=config.base_url,      # 兼容任何 OpenAI 协议的 API
    skills_dirs=["./skills"],      # SKILL.md 技能包目录
    tools=[*feishu_tools, *cron_tools],  # 自定义工具
)

async for chunk in client.stream(prompt, session_id):
    if isinstance(chunk, TextDeltaChunk):
        response += chunk.text
```

29 个内置工具、流式输出、会话管理、上下文压缩、权限控制、多模型适配——全在这个 `client` 里面。你要做的只是告诉它用什么模型、有哪些额外工具、工作目录在哪。

这里面有两套扩展机制值得说一下：

- **`tools`**：Python 函数。你想让 AI 能发飞书消息、能创建定时任务，写成 tool 注册进去就行。
- **`skills_dirs`**：SKILL.md 文件，纯 Markdown。告诉 AI 这个技能是什么、什么时候该用。不用写代码，直接借鉴了 OpenClaw 的 SKILL.md 设计。

有了 Cody 兜底，我们就可以把精力集中在真正有意思的部分——Gateway 层和上层的业务逻辑。

## 我们真正要写的东西

省掉 Agent 执行层之后，CodyClaw 自己要写的核心逻辑就清晰了。下面逐个展开，每个都带核心代码。

### 飞书接入：一个线程隔离的 trick

OpenClaw 用 Baileys 逆向 WhatsApp Web 协议，我们没必要这么硬核。飞书有官方 SDK `lark-oapi`，支持 WebSocket 长连接——连接从你的机器主动发出去，不需要公网 IP。

```
你的手机 ──→ 飞书服务器 ──→ 你的服务（WebSocket 长连接）
```

但这里有个坑。飞书的 `lark-oapi` SDK 在 import 的时候就把当前的 event loop 捕获到了模块级变量里。如果你的服务跑在 uvicorn 上，SDK 会抓到正在运行的 loop，然后 `start()` 里调 `loop.run_until_complete()`——直接报 "this event loop is already running"。

解决方案有点 hack，但管用：在独立线程里建一个全新的 event loop，然后**直接替换 SDK 模块里的 loop 变量**：

```python
def _run_ws_in_thread(self) -> None:
    import lark_oapi.ws.client as ws_module

    new_loop = asyncio.new_event_loop()
    asyncio.set_event_loop(new_loop)
    ws_module.loop = new_loop  # 直接替换 SDK 模块级的 loop 变量

    self._ws_client = lark.ws.Client(...)
    self._ws_client.start()  # 阻塞在独立线程里，不影响 uvicorn
```

SDK 线程收到消息后，要回到 uvicorn 的 asyncio 循环里处理。靠的是 `asyncio.run_coroutine_threadsafe()`：

```python
def _sync_on_message_event(self, *args) -> None:
    event = args[-1]  # 兼容 WebSocket / Webhook 两种调用签名
    asyncio.run_coroutine_threadsafe(
        self._on_message_event(event), self._loop
    )
```

这两段代码解决了飞书接入层最核心的问题：**怎么在一个 async 服务里跑一个同步的 SDK**。剩下的收发消息、@mention 解析、用户名缓存（OrderedDict 做 LRU，上限 1000 条）都是常规操作。

### 消息路由：三级解析

消息进来之后，第一件事是判断交给哪个 Agent。配置长这样：

```yaml
agents:
  - agent_id: "assistant"
    trigger_mode: "all"          # 所有消息都响应
    allowed_users: ["ou_xxx"]

  - agent_id: "ops"
    trigger_mode: "mention"      # @ 才响应
    allowed_groups: ["oc_xxx"]
```

路由是三级优先级：

```python
def resolve(self, msg: IncomingMessage) -> Optional[AgentConfig]:
    # 第一优先级：显式的群组绑定
    if msg.chat_type == "group":
        agent_id = self._group_bindings.get(msg.chat_id)
        if agent_id:
            agent = self._agents[agent_id]
            if agent.trigger_mode == "mention" and not msg.is_mention_bot:
                return None  # 群里没 @ 就不响应
            return agent

    # 第二优先级：显式的用户绑定
    if msg.chat_type == "p2p":
        agent_id = self._user_bindings.get(msg.sender_id)
        if agent_id:
            return self._agents[agent_id]

    # 第三优先级：走默认 Agent
    return self._resolve_default(msg)
```

单聊和群聊有一个关键区别：**单聊总是触发**（你私聊机器人肯定是要跟它说话），**群聊要看 trigger_mode**（你在群里说话不一定是在跟机器人说话）。

### 调度核心：一条消息的完整生命周期

路由找到 Agent 之后，消息进入 `dispatcher.py` 的 `dispatch()` 方法。这是整个系统最核心的函数，拆开讲。

**第一步，拼装上下文。** 不是直接把用户消息丢给 AI，而是往里注入好几层信息：

```python
# 飞书元信息（让 AI 知道消息来自哪里、谁发的）
context_parts = [
    f"[Feishu context] chat_id={msg.chat_id} sender_name={msg.sender_name}",
]
# 用户画像（跨对话的长期记忆）
user_profile = self._user_memory.get_for_prompt(msg.sender_id)
if user_profile:
    context_parts.append(user_profile)
# 群聊历史（让 AI 知道"前面大家在聊什么"）
if msg.chat_type == "group":
    history = await self._fetch_history_safe(msg.chat_id)
    if history:
        context_parts.append(self._format_chat_history(history))
# 用户的实际消息
context_parts.append(msg.content)
```

**第二步，流式执行。** 调用 Cody 的 `stream()` 接口，逐 chunk 处理。每个用户同时只有一个在跑的任务，发"取消"可以中断：

```python
run = ActiveRun(user_id=msg.sender_id, cancel_event=asyncio.Event(), ...)
self._active_runs[msg.sender_id] = run

async for chunk in client.stream(context, session_id=session_id,
                                  cancel_event=run.cancel_event):
    if isinstance(chunk, TextDeltaChunk):
        run.accumulated_text += chunk.content
        await self._update_streaming_card(run, msg)

    elif isinstance(chunk, ToolCallChunk):
        run.tool_calls.append(chunk.tool_name)
        if chunk.tool_name in _FEISHU_MESSAGE_TOOLS:
            run.has_sent_feishu_message = True  # AI 主动发了消息

    elif isinstance(chunk, DoneChunk):
        self._sessions.set(session_key, chunk.session_id)  # 持久化会话
```

**第三步，流式卡片。** AI 生成回复可能要 10-30 秒。我们先发一张"思考中"的卡片，然后每 1.5 秒更新一次：

```python
_CARD_UPDATE_INTERVAL = 1.5  # 再快会触发飞书速率限制

async def _update_streaming_card(self, run, msg, force=False):
    now = time.monotonic()
    if not force and (now - run.last_card_update) < _CARD_UPDATE_INTERVAL:
        return  # 节流

    content = run.accumulated_text.strip() or "⏳ 思考中..."
    card = build_streaming_card("执行中", content, "running")  # 蓝色卡片

    if run.card_message_id is None:
        run.card_message_id = await self._channel.send_card(msg.chat_id, card)
    else:
        await self._channel.update_card(run.card_message_id, card)
```

卡片上还能看到 AI 调了哪些工具（带 ✓ 标记）。内容超 4096 字符自动截断——飞书的硬限制。

**第四步，收尾。** 三种情况，保证用户不会收不到回复：

```python
async def _finalize_streaming_card(self, run, msg):
    if run.card_message_id:
        # 有流式卡片 → 更新为"完成"（绿色）
        await self._channel.update_card(run.card_message_id, done_card)
    elif run.accumulated_text and not run.has_sent_feishu_message:
        # 没卡片 + AI 也没主动发消息 → 兜底回复
        await self._channel.send_card(msg.chat_id, done_card)
    # else: AI 通过工具发了消息，不需要额外输出
```

### 会话管理：懒过期 + 持久化

群聊共享上下文（所有人看同一个对话），单聊按人隔离：

```python
def _get_session_key(self, agent_config, msg):
    if msg.chat_type == "group":
        return f"{agent_config.agent_id}:{msg.chat_id}"
    return f"{agent_config.agent_id}:{msg.sender_id}"
```

`SessionManager` 不跑后台清理，而是**懒过期**——下次 `get()` 才检查：

```python
def get(self, key: str) -> Optional[str]:
    session_id = self._session_map.get(key)
    if session_id is None:
        return None
    if time.time() - self._last_active.get(key, 0) > self._idle_timeout:
        self._expire(key)  # 超过 24 小时没动静，过期
        return None
    return session_id
```

每次 `set()` 同步写 SQLite，重启从 DB 恢复未过期的会话。

### 用户记忆：1500 token 的画像

会话是有时效的（24 小时），记忆是永久的。每个用户一个 JSON 文件（`~/.codyclaw/users/{user_id}.json`），AI 通过工具调用写入。每次消息进来，画像注入到 prompt 最前面：

```python
def get_for_prompt(self, user_id: str) -> str:
    entries = self._load(user_id)
    if not entries:
        return ""
    budget = 1500 * 4  # 1500 token ≈ 6000 字符
    lines = ["[User profile]"]
    used = len(lines[0])
    for entry in entries:
        line = f"- {entry.content}"
        if used + len(line) > budget:
            break
        lines.append(line)
        used += len(line)
    return "\n".join(lines)
```

上限 100 条，FIFO 淘汰。比 OpenClaw 的向量数据库简单得多，但记忆条目就几十条时，全量注入比语义检索不容易漏。

### 自定义工具：闭包工厂

让 AI 能发飞书消息、建定时任务、管记忆——都通过自定义 tool 实现。所有工具通过**闭包捕获 getter**，而不是直接引用实例：

```python
def make_feishu_tools(get_channel):
    async def feishu_send_text(ctx, chat_id: str, text: str) -> str:
        channel = get_channel()  # 每次调用时取最新实例
        if channel is None:
            return "Error: Feishu channel is not available."
        await channel.send_text(chat_id, _fix_mentions(text))
        return "Message sent."
    return [feishu_send_text, ...]

# 注册时传 lambda
self._feishu_tools = make_feishu_tools(lambda: self._channel)
```

为什么不直接传 `self._channel`？因为初始化时 channel 可能还没好，后续也可能被重建。getter lambda 每次拿活实例，组件完全解耦。

AI 发消息时自然地写 `@ou_xxx` 来 at 人，`_fix_mentions()` 用正则自动转成飞书的 `<at>` 标签——对 AI 透明。

### Cron 定时任务：AI 自建 + 跨执行记忆

APScheduler 调度，支持两种格式——AI 用哪种都行：

```python
if "every" in schedule_lower or schedule_lower.endswith(("h", "m")):
    trigger = IntervalTrigger(minutes=self._parse_interval(schedule))
else:
    trigger = CronTrigger.from_crontab(schedule, timezone=task.timezone)
```

AI 通过 `create_cron_task` 工具建任务时会先验证 Agent 是否存在。每个 cron 任务有自己的持久化会话（`cron:{task_id}`），AI 跨多次执行能积累上下文——比如今天的新闻摘要可以参考昨天提过什么。

结果发到飞书，卡片带下次执行时间。

### Cody Client：每个 Agent 一个引擎

每个 Agent 独立一个 Client 实例，用 double-checked locking 防并发创建：

```python
async def get_or_create_client(self, agent_config):
    async with self._client_locks[agent_id]:
        if agent_id not in self._clients:
            client = (
                Cody()
                .workdir(agent_config.workdir)
                .model(agent_config.model)
                .interaction(enabled=False)  # 审批走飞书，不走 Cody 内置
                .circuit_breaker(max_tokens=500_000, max_cost_usd=2.0)
                .skill_dirs([_BUILTIN_SKILLS_DIR, _MANAGED_SKILLS_DIR])
            ).build()
            await client.__aenter__()
            self._clients[agent_id] = client
    return self._clients[agent_id]
```

`.interaction(enabled=False)` 关掉了 Cody 内置的审批——审批走飞书消息。`.circuit_breaker()` 设了 token 和费用上限，防止 AI 跑飞。

## 跑起来了

项目结构：

```
codyclaw/
├── main.py          ← FastAPI 应用入口
├── config.py        ← YAML 配置加载（支持 ${ENV_VAR}）
├── channel/         ← 飞书 WebSocket 接入
├── gateway/         ← 路由、调度、会话、记忆
├── automation/      ← Cron 调度、事件总线
├── web/             ← 管理后台
└── skills/          ← SKILL.md 技能包
```

`docker compose up -d` 一键跑。首次启动没有配置文件会进 Setup 向导，浏览器里填好飞书 App ID 和 API Key 就行。

| Boot 启动脚本 | BOOT.md 自然语言启动 | 支持 |
| 流式输出 | 多渠道流式推送 | 飞书卡片实时更新 |
| 浏览器自动化 | Playwright + CDP | 不做 |
| 多端 App | iOS / Android / macOS | 不做 |
| 插件市场 | ClawHub 生态 | 不做 |

核心功能基本都有了。砍掉的是多渠道、浏览器、移动端 App 这些"外延"——对于一个跑在飞书上的个人/团队 AI Agent，这些本来也用不着。

---

## 最后说两句

写这篇文章的目的不是要做一个 OpenClaw 的替代品。说实话，OpenClaw 的工程量和社区生态不是一个周末项目能比的。

我们真正想做的事情是：**通过自己动手造一只，把上一篇拆解出来的技术细节从"看懂了"变成"摸过了"**。

上一篇你知道了 OpenClaw 有消息路由、有会话管理、有 cron、有执行审批、有 SKILL.md、有 BOOT.md。但那些都是别人的代码。自己写一遍之后你会发现：消息路由就是几十行 if-else，会话管理就是一个 `{agent_id}:{user_id}` 的 key，cron 就是 APScheduler 加个 SQLite，执行审批就是在消息流里插一个 asyncio.Event。每一个单独拿出来都不复杂，OpenClaw 的厉害之处在于把它们粘成了一个 7×24 在线的整体。

而粘合这件事本身，真没那么玄——核心逻辑不到 800 行 Python。
